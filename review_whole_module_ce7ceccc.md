## Review

**0 critical, 7 warnings, 0 suggestions**

🟡 **7 Warnings**

- `src/mod_mana_speedflying.cpp:576` - `applied = std::min(g_cfg.boostSpeed, current + boostOffset)` clamps the *unboosted* state speed too. `boostSpeed` is only forced to be >= `diveSpeed` (line 660), so if an operator sets ClimbSpeed/LevelSpeed above BoostSpeed (e.g. levelSpeed=10, boostSpeed=3), normal level/climb flight is silently clamped below its configured rate even when no boost is active. The ceiling should only apply while a boost offset is present (or boostSpeed must be clamped to >= max of all three state speeds).
- `src/mod_mana_speedflying.cpp:359` - The addon message is unauthenticated. Any client can send `WXLMS\t1B...` regardless of whether it actually runs wxl-mount-anim. Because the boost path allows accelerating up to BoostSpeed (default 1600%), a forged link lets a player exceed the 'at worst one of the three configured speeds' claim in the README/comment. The sender is never checked (no mount state, no rate limit beyond client-side throttling), so this is a gameplay-integrity hole if the channel is open.
- `src/mod_mana_speedflying.cpp:372` - `g_states[player->GetGUID().GetRawValue()]` default-inserts a PlayerState for any WXLMS addon message, before the `advfly != '1'` early return. A non-AdvFly mount (or a spammer) creates an entry that is only cleaned on logout, so the map grows for clients that never use the feature properly.
- `src/mod_mana_speedflying.cpp:443` - OnPlayerUpdate reads the PlayerState under g_lock, releases it, computes for the whole tick, then re-acquires to write back (line 595). If OnPlayerBeforeSendChatMessage (line 371) ever runs on a different thread than PLAYERHOOK_ON_UPDATE, the intervening lock is insufficient and its SetTarget/ActivateBoost updates can be overwritten by the stale write-back. If both hooks are guaranteed to be on the player's map thread the mutex split is harmless, but the code implies uncertainty.
- `src/mod_mana_speedflying.cpp:384` - `st.announced` is never reset when the link drops (advfly='0' at line 374 or timeout at line 471). On re-link, the first-contact announce is gated only by `now - st.lastAnnounce >= 5000`, so a client that reconnects shortly after a drop can miss the speed announce and display defaults until the slow resend fires.
- `src/mod_mana_speedflying.cpp:668` - OnAfterConfigLoad clears `g_states` unconditionally. If a config reload happens while a player is flying, no update path restores the mount speed; the player keeps the last blended MOVE_FLIGHT rate until the client's next heartbeat recreates the state. Also, g_cfg is written here without g_lock while OnPlayerUpdate reads it, a data race unless reload is guaranteed to run on the world thread.
- `src/mod_mana_speedflying.cpp:423` - OnPlayerUpdate returns immediately when the player is not flying, so `sinceLink` stops advancing (the timeout can never fire on the ground) and any active boost/stacks are frozen rather than reset. If the client link dies right as the player lands, the state stays eligible until they fly again, at which point the stale `lastSent`/`current` resume instead of being restored.

**Summary:** A dense but generally sound state-machine module; the transition math, boost carry accounting and overflow guards are careful. The most substantive issues are the boost ceiling being applied to unboosted state speeds (silent slowdown on non-default config) and the fully unauthenticated addon link allowing forged boost speed. Remaining findings are lower-impact memory and link-lifecycle edges.
